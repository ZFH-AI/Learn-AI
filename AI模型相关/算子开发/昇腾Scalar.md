# 1、Scalar Unit
Scalar Unit 标量运算单元：负责标量计算、地址计算、指令参数构造、以及其他流水线分发指令

Scalar Unit 指令分发，理想情况下Scalar 应能及时将指令分发到各流水的issue队列，使所有流水线保持满载并行，

当Scalar单元本身成为瓶颈，无法及时为其他流水线分发指令，导致流水线产生bubble（空闲周期）时，这种现象称为ScalaBound

## 1.1 ScalarBound对算子性能的影响
- 影响一：导致流水中断，破坏指令并行性
- Scalar本身的高耗时直接拖慢算子总耗时

## 1.2 calarBound原因分析
主要有以下三种原因
```shell

|  原因        |  描述                                 |是否是Scalar自身问题
---------------------------------------------------------------------------------
| Load依赖阻塞 | Scalar计算依赖Load指令的执行结果，Load  | 是
|             | 未完成时Scalar无法推进                  | 是
--------------------------------------------------------------------------------
| 计算指令过多 | Scalar计算指令过多，分发速度跟不上其他流  | 是
|             | 水线消费速度                             |
---------------------------------------------------------------------------------
| 反压阻塞     | 某个或多个issue队列已满，反向阻塞Scala   | 一般不是
|             | 无法继续分发                            |
---------------------------------------------------------------------------------
 
```

### 1.2.1 Load/Stroe产生的原因
编译器会尽量使用寄存器保存变量，但寄存器的个数有限，当活跃变量数超过可用寄存器个数时，编译器必须选择一个寄存器，将当前值通过store指令保存到栈内存上，
这个过程称为寄存器Spill（register spill）,等到需要再次使用该变量时，编译器在通过Load指令从栈内存中读回寄存器中

寄存器Spill过程对程序员不可见，因此在算子开发中容易被忽略，然而算子的编码方式会显著影响编译器的寄存器分配策略，进而影响Spill的频率和Load/Stroe指令的
总量，以下编码模式容易加剧寄存器Spill

- 类成员变量过多，
- 结构体变量的拷贝
- 变量生命周期过长
- 多级指针引用

## 1.3 通用优化模式
```shell

| 模式         | 核心思想                              | 典型手段    
+-----------------------------------------------------------------------------------+
| 减少内存访问  | 减少Load/Store指令数，降低寄存器Spill  | - 局部变量替代成员变量
|              |                                      | - 静态创建LocalTensor
|              |                                      | - 消除多级指针
+-----------------------------------------------------------------------------------+
| 改善指令缓存  | 消除ICache-Miss，保证Scalar指令流的连续| - ICache预取
|              |                                      | - 精简代码
|              |                                      | - 循环拆分减少代码量
+-----------------------------------------------------------------------------------+
| 改善数据缓存  | 提高数据访问的空间/时间局部性           | - 变量定义贴近使用
|              |                                      | - 避免大结构体
|              |                                      | - 减少数据拷贝
+----------------------------------------------------------------------------------+
| 消除编译器优化| 帮助编译器完成常量传播、常量折叠优化     | - 去除结构体中的冬天索引数组
| 障碍         |                                       | - 用值类型代替指针类型
+----------------------------------------------------------------------------------+

```

## 1.4 ScalarBound诊断流程
当怀疑算子存在ScalarBound时，建议按以下步骤诊断和处理：
```shell

>> step 1  采集Profiling数据
         |-- 工具：msprof或者cannsim仿真
         |
         |-- 关键命令：msprof --application=./your_op --output=./prof_data
         |
         |-- 输出：各流水线耗时（含Scalar）、instr_popped_log.dump文件等

>> step 2 判断Scalar耗时占比
         |-- 查看各pipeline的cycle分布
         |-- 阈值建议：Scalar耗时超过其它pipeline的耗时，可能存在ScalarBound
         |-- 更准确的判断：通过打点图观察其他pipeline（Cube/MTE）是否出现明显bubble

>> step 3 分析Scalar瓶颈类型
         |-- 检查 instr_popped_log.dump → 统计Load/Store指令占比
         |     |--  Load/Store占比 > 30% → 寄存器Spill问题（进入Step 4a）
         |
         |-- 绘制 PC vs Cycle 图 → 检查icache miss
         |     |-- 出现长水平线段 → I-Cache问题（进入Step 4b）
         |
         |-- 检查 branch预测统计 → 分支预测失败率
               |-- 失败率高 → 分支预测问题（进入Step 4c）

>> step 4 针对性优化
         |-- 4a: 寄存器Spill --> 分析Load和Store变多的原因
         |
         |-- 4b: I-Cache Miss → icache预取；精简代码体量
         |
         |--  4c: 分支预测 → 循环主尾块分离；显式for循环

```
