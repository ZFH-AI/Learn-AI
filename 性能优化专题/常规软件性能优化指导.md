# 1、概览
软件性能优化的目标就是让处理器能够运行的更高效，性能优化一般分三个层次
- **系统层次** 系统的控制流程和数据流程，优化主要考虑如何减少消息传递个数，如何充分利用硬件的性能
- **算法层次** 不变更接口的情况下，使用更高效的算法替换现有算法
- **代码层次** 代码优化

## 1.1 系统层次
性能的问题，应该是整个开发周期都需要考虑的问题。然而对于公司的大部分软件开发周期，通常情况下，我们开发人员只有等到开发工作收尾的时候，才会进行性能方面的考量。这样导致的后果，就是后期性能调优的时候，优化一次，对早期代码开发就吐槽一次。如果仅仅是代码层面还好，可以纠正。如涉及到系统框架的设计，那改动量是巨大和存在风险的。

基于这些性能优化问题的存在，我们根据优化的经验，总结了在模块开发设计阶段，就应该考虑衡量的性能规范。希望我们的软件开发人员能够重视和执行，从而保证我们软件版本的高质量交付

- 1、识别性能关键路径，针对关键路径进行重点性能设计
- 2、进行性能分解，确保性能指标被落实
- 3、简化通信设计，缩短通信路径，减少交互次数
- 4、性能关键路径上，数据拷贝最小化设计, 避免大数据拷贝
- 5、避免设计集中的耗时处理过程，使CPU占用率处于正常水平
- 6、性能关建路径需要尽量避免严重的锁冲突
- 7、通过软硬件协同设计，提升系统性能

## 1.2 代码层次
常用如下方式来提高处理器的运行效率

- 1、减少程序的指令数：主要方式：代码简洁、减少函数调用、用空间换时间、减少冗余保护
- 2、减少处理器不擅长的操作：主要方式：少用乘、除、求余等操作、尽量减少分支
- 3、优化内存访问：主要方式：减少内存读写的交互、避免伪共享等
- 4、充分利用编译优化：
```shell
-O1（基础优化）：旨在提高执行速度，同时几乎不增加编译时间
   该级别开启最基本的优化，不进行任何降低编译速度的算法。它主要减少指令数量，且极少增加代码体积。
     - 指令调度：重排汇编指令以减少 CPU 流水线停顿。
     - 常量折叠与传播：在编译时计算好 2 + 3 这种常量，或把已知常量的变量替换为常量。
     - 死代码消除：删掉代码中永远不会执行到的分支或从未被使用的变量。
     - 公共子表达式消除（简易版）：合并重复的计算。
     - 局部变量寄存器分配：将常用变量优先放入 CPU 寄存器而非内存




-O2（推荐优化）：应用几乎所有不涉及“速度与空间权衡”的优化算法，是最常用的生产环境默认选项
    包含 -O1 的所有优化，并加入几乎所有不需要牺牲代码体积的优化算法。编译时间会显著增加。
      - 严格别名分析：假设不同类型的指针不会指向同一内存地址，从而允许 CPU 更激进地缓存数据。
      - 尾调用消除：将函数末尾的递归调用转换为循环，防止栈溢出并减少函数调用开销。
      - 内联函数（部分）：自动将一些极小的函数体直接展开到调用处，消除函数调用开销
      - 更激进的寄存器分配：优化寄存器使用，尽量减少对内存的读写（Load/Store）

-O3（激进优化）：开启高耗时及可能增加代码体积的优化，追求极致的执行速度
    包含 -O2 的所有优化，并开启可能大幅度增加可执行文件体积、甚至在某些情况下由于缓存失效（Cache Miss）反而导致性能下降的激进优化
      - 动向量化（Auto-Vectorization）：利用 CPU 的 SIMD（单指令多数据）指令集（如 AVX、NEON），让一条指令同时处理多个数据（例如同时计算 4 个浮点数加法）
      - 激进的函数内联：不顾代码体积的增长，大量将函数展开，极大地减少函数跳转带来的开销。
      - 循环展开（Loop Unrolling）：将循环体复制多份以减少循环计数器的判断和跳转次数。
      - 循环剥离与转换：重新排列循环结构，使数据访问更符合 CPU 缓存的局部性原理

```
- 5、利用逻辑短路操作，减少判断条件的运行
- 6、if语句，使用预测宏提高分支的执行效率
- 7、当函数的入参为结构体时，应使用指针传递
- 8、多核可能同时访问的代码中如果包含全局变量、结构体或者数组，那么这些全局变量、结构体和数组就可能存在伪共享的风险。伪共享对性能影响很大，要尽量避免。需要考虑伪共享的规避设计
```shell
    对于可能产生伪共享的代码场景，我们需要进行如下考量：

    （1）      如果这些全局变量、结构体和数组都是只读属性，一次赋值，后面都是读取，可以不用考虑伪共享，因为只读不会导致伪共享。

    （2）      如果真的存在伪共享的可能，检视一下是否真的需要存在。有一些维测使用到的全局变量导致的伪共享，这些维测全局变量是否冗余？

    （3）      如果无可避免，考虑下面的伪共享解决方案：

              u  利用空间换时间。每个核独占一个cacheLine

              u  降低伪共享碰撞的概率，例如先判断一下是否需要访问这些伪共享点
```
- 9、循环体内要保证循环最小化原则，与循环无关的操作都提取到循环外
- 10、多重循环，最长循环放在最里层
- 11、对多维数组的访问要符合cache的局部性
- 12、避免重复多级寻址
- 13、减少指针地址的解引用
- 14、代码的作用域仅在分支块内，就不要定义成函数级
- 15、把相关代码放在相邻的位置
- 16、避免变量的数据类型定义过大
- 17、特性分支/维测跟踪应使用独立的分支函数，并和主流程代码隔离，调用特性分支入口函数前，使用特性/跟踪开关进行判断
- 18、关键路径且调用点很少的函数默认定义inline或使用宏；非关键路径函数默认定义非inline
- 19、去除冗余的入参合法性判断保护
- 20、Unlikely场景的代码块如果较大[y(2] ，则将代码块封装成函数，减少主流程指令块
- 21、减少不必要的内存操作
- 22、谨慎使用原子和锁操作的接口，尽量找到优化方案
```shell
    【说明】因为我们L2是多核并行化编程，当有一些敏感数据不允许被多个线程同时访问的时候，就需要用到原子操作和锁，避免数据被多个线程同时操作。
           原子操作和锁操作接口的性能开销也比较大，需要我们重点关注。对于这一块，我们的优化建议有：
    
    (1)    读写分离替换独占锁。对于读多写少的操作，可以考虑读写锁，增加读的操作量。
    
    (2)    考虑每一个核独占cacheline的共享方式来代替原子操作和锁，但需要权衡内存占用开销。
    
    (3)    原子操作的性能消耗比锁低，能使用原子操作实现锁的功能，优先考虑原子操作。
    
    (4)    如果使用锁，尽量缩小锁定的代码范围。
    
    (5)    优化代码，让持有锁的时间尽量短
```
- 23、使用其他方式减少函数调用：常用方式：使用inline函数（小于10行）、减少函数调用层次
- 24、使用其他方法替换乘除法或者取模运算在代码中的使用
- 25、开关判断提前，减少函数入栈出栈
- 26、使用其他方式替代全局变量的使用
```shell
    减少全局变量的使用有三个好处：
    
    l     一般编译器不轻易对全局变量的相关操作做优化，将全局变量赋值给局部变量，函数中使用局部变量去进行操作，可以帮助编译器明确可以优化的范围。
    
    l     多线程场景下，使用局部变量可以避免多线程之间对全局变量使用的冲突。
    
    l     提高代码的可修改性
    
    一般可以使用的方法有：使用局部变量替换全局变量
```
- 27、函数入参可以多于4个，不要超过8个
