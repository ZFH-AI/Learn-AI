# 1.问题诊断
Agent 长对话失忆——窗口满了，旧内容被驱逐，没有持久化兜底。不是模型忘了，是根本没存过。同样的错误跨 Session 重演——没有机制把这次学到的带进下次，每次冷启动都是白纸。简单查询花了十倍 token——平铺检索把整篇文档塞进来，一句摘要就够了。
三个症状，同一个根因：我们一直把上下文窗口当内存用，从来没有把它当数据库管。

# 2.核心洞察
数据库里的数据有完整的生命周期——写入有策略，索引有层级，查询感知代价，过期有清理，关闭有归档。没有人会把数据库当无界缓冲区用。

但现有的 Agent 记忆系统就是这么对待上下文的：抽取一下，embed 一下，存进去，查出来。写入策略是什么？不知道。索引怎么组织？一层平铺。窗口满了怎么办？压缩一下。Session 结束了？什么都不留。

上下文窗口是 Agent 最贵也最稀缺的资源，却是整个系统里管理最粗放的一层。

设计原则
ContextEngine 的回答是：用管数据库的方式管上下文。

不同语义的数据用不同的写入策略——可变状态覆盖，不可变历史追加。

索引分层，按需加载，只付你用到的 token 代价。

写入原子，中断可检测可修复。

Session 结束显式归档，下次冷启动有据可查。

把上下文窗口当数据库管，不是当内存用。该存什么、存多少、怎么取、什么时候丢、丢前留什么——每一步都要有明确的答案。


## 2.1.消息到达阶段——轻量感知，不阻塞推理
消息刚到的时候，时间最紧。我们只做两件事：意图分类，判断这条消息是在问记忆类问题还是能力类问题；然后触发异步预取，在后台开始搜索相关上下文。

关键约束是：这一步不能做任何同步加载。50 毫秒以内必须完成，超时就静默跳过。

## 2.2.推理准备阶段——上下文组装的核心工程
这是最复杂的阶段，也是花费最多设计的地方。

首先是冷启动和会话恢复。新会话第一轮，要把用户画像、历史偏好、上次未完成的任务一并注入——让 Agent 一开始就认识用户，而不是每次都从陌生人开始。

然后是预算规划。当前窗口剩余多少 token，按 L0 优先、L1 其次、L2 最后的顺序分配，确保永远不超预算。

然后是召回。这里有一个反直觉的设计，我后面会专门讲。

## 2.3.工具调用阶段——经验注入
调用工具之前，我们从 Skill 库里加载这个工具的历史使用经验：上次最优的参数组合，已知的失败 Pattern。如果当前参数命中了历史失败 Pattern，可以直接拦截并警告。

工具返回之后，结果可能很大——比如 grep 返回了五千行。我们在这里做结果凝练，提取核心事实再注入上下文；同时把有长期价值的事实提取出来持久化。

## 2.4.轮次结束阶段——核心写入
这是整个写入路径最关键的阶段。

增量提取：只处理本轮新增的消息，不重复处理历史。LLM 先读已有记忆，确认是新信息再提取。

原子写入：四步有序写入——先写内容，再写关系，再写摘要，最后写 meta.json 作为提交标志。任何中断都可以检测和修复。

异步索引：写入完成后把 embed 和向量 upsert 交给后台处理，同步路径约 50 毫秒，不阻塞响应。

## 2.5.压缩阶段——保信号，丢冗余
窗口快满时，先给每个节点打分——Profile 和活跃任务设为不可驱逐，其他按访问热度和相关性排序。然后对语义重叠的片段归并，对早期对话历史做滚动压缩，生成 Summary Chain 替换原始消息。

## 2.6.会话结束阶段——为下次留好遗产
已完成任务归档为 Case 节点，未完成任务生成 Handoff 快照，整个会话生成摘要写入 Profile。这些内容在下次 Session 的冷启动阶段被读取——形成闭环。
