
# 1、数据库选型
| 数据库/工具选型 | 类型 | 推荐落地场景 |
| :--|:--|:--|
| Pinecone / Zilliz Cloud | 全托管云服务 | 开箱即用，不想维护基础设施。搭配 Cohere Rerank + GPT-4o 是最快商用的方案|
| Qdrant | 开源 + 托管 | Rust 编写，内存管理优秀，性能极高。适合企业级私有化部署|
| Weaviate / Elasticsearch | 开源 + 托管	| 自带极其成熟的 BM25 + 向量混合检索（Hybrid Search），专有名词较多的场景首选|
| Milvus	| 开源分布式	| 适合十亿至百亿级别的超大规模企业级检索平台|
| Chroma / FAISS	| 本地库/嵌入式	| 极轻量，无需部署独立服务。非常适合本地开发、个人知识库项目验证|

# 2、Embedding选型

## 2.1、选型核心考量因素
| 考量维度 | 说明 | RAG场景优先级 |
| :--| :-- | :-- |
| 检索准确率	| 在 MTEB Retrieval 等基准上的 NDCG@10、Recall 等指标，直接决定最终答案质量	| ⭐⭐⭐⭐⭐|
| 最大序列长度	| 单个文本块能容纳的最大 token 数，必须与分块策略匹配，尤其处理长文档时	 | ⭐⭐⭐⭐⭐ |
| 多语言/中文支持 |	处理中文、多语言混合文档的能力，非纯英文场景的决定性因素 |	⭐⭐⭐⭐⭐ |
| 部署方式与隐私	| 开源本地部署（数据不出域，可控性高） vs 商业 API（便捷，但数据需出域）|	⭐⭐⭐⭐ |
| 推理成本 |	API 按 token 计费，或本地 GPU 资源的硬件与电力开销	| ⭐⭐⭐⭐ |
| 嵌入维度 |	维度越高表达能力通常越强，但存储和检索速度开销越大；可变维度模型可灵活平衡 |	⭐⭐⭐ |
| 混合检索支持 |	是否原生输出稀疏向量（如 SPLADE、BGE-M3），便于与 BM25 等结合提升召回率	| ⭐⭐⭐ |
| 指令跟随能力 |	能否根据提示（如“用于检索”）动态调整向量，提高意图匹配度 |	⭐⭐ |
| 领域适应性	| 代码/医学/法律等垂直领域是否有专用模型，通用模型是否便于微调	| ⭐⭐ |
