# 1、C/C++基础知识
## 1.1、volatile 关键字
核心作用：
- 防止编译器对该变量相关的代码进行优化，确保程序每次读取或修改该变量时，都直接在内存或硬件寄存器中进行，而不是使用CPU寄存器或缓存中的旧值

三大特征：
- 易变性：告诉编译器，该变量的值随时可能在当前流程之外被改变
- 不可优化性：禁止编译器对该变量进行寄存器缓存、删除看似无用的读写指令等优化操作
- 顺序性：保障多条volatile变量的指令顺序不会被编译器随意重排

常见误区
- volatile 不能保障操作的原子性
- volatile 不能替代多线程锁

## 1.2、智能指针
Smart Pont 智能指针是C++基于RAII机制用于管理动态内存的类模板，它的核心作用是自动释放不在使用的内存，避免内存泄露和野指针

核心作用原理：智能指针的本质是一个对象，但它通过重载 * 和 -> 运算符，使得自己用起来像一个普通指针。
- 构造时绑定：在创建智能指针对象时，将通过new申请的原始指针传递给它，由对象内部的私有成员变量保存
- 析构时释放：当前智能指针对象超出其作用域时，编译器会自动调用该对象的析构函数，并在析构函数内部调用delete释放原始指针指向的内存

智能指针的分类：C++11 标准引入了三种主流的智能指针（位于 <memory> 头文件

| 智能指针类型 | 所有权模型 | 引用计数变化 | 拷贝/移动支持 | 核心应用场景 |
| :-- | :-- |:--|:-- | :-- |
|std::unique_ptr | 独占（唯一一个），同一时间只能有一个unique_ptr指向该内存|无计数开销|禁止拷贝、允许移动| 绝大多数常规内存管理，低开销首选|
|std::shared_ptr | 共享（多人），多个 shared_ptr 可以共同指向同一个对象，该对象在“最后一个引用者”销毁时才会被释放 |拷贝时 +1，销毁时 -1| 允许拷贝，允许移动|资源需要被多个模块共享、生命周期不确定|
|std::weak_ptr   | 它是 shared_ptr 的辅助者，只观测，不占有。它指向 shared_ptr 管理的对象，但不会增加引用计数, 不能直接访问对象|不影响主计数|允许拷贝，允许移动|解决循环引用、缓存实现、观察者模式|

## 1.3、内存墙（Memory Wall）
产生原因：
 - CPU 突飞猛进 VS 内存步履蹒跚

带来的核心问题
- 处理器饥饿（Processor Starvation）：CPU 执行一条指令可能只需 0.5 纳秒，但从内存读取一个数据却需要 50-100 纳秒。这意味着 CPU 每执行几步，就要停下来等几百个周期
- 功耗浪费：在现代 AI 计算（如大语言模型推理）中，大量的能量并非消耗在计算上，而是消耗在将数据从内存搬运到 CPU/GPU 的过程中（即数据搬运功耗）

现有的解决方案：
- 多级缓存机制（Cache Hierarchy）：
  
  -- 原理：在 CPU 内部放置体积小但速度极快的 SRAM（L1, L2, L3 缓存）
  
  -- 作用：利用时间与空间局部性，把常用的数据提前放到缓存里，减少直接访问内存的次数
  
-  高带宽内存技术（HBM, High Bandwidth Memory）

   -- 原理：不再用传统的插槽内存，而是通过 3D 堆叠技术，把多层内存芯片直接“贴”在 GPU/CPU 芯片旁边

   -- 应用：当前主流的 AI 显卡（如 NVIDIA H100, B200）全部依赖 HBM 来对抗内存墙

- 存内计算（CIM / PIM, Computing in Memory）

  -- 原理：打破“计算与存储分离”的传统冯·诺依曼架构，直接在存储芯片内部集成计算单元

  -- 作用：数据不需要在内存和处理器之间“跑来跑去”，在原地就能完成计算，彻底消除搬运延迟

- 软件与编译层面的代码优化

   -- 原理：写代码时，保证数据在内存中是连续存储的，方便 CPU 批量预取（Prefetch）

   -- 应用：在 C/C++ 中，尽量使用连续的数组（数据结构对齐），减少离散的链表或指针跳转，提高缓存命中率

## 1.4、内存屏障（Memory Barrier）
内存屏障（Memory Barrier / Memory Fence）是一条 CPU 指令，它的核心作用是限制 CPU 和编译器的指令重排（Reordering），并强制同步多核 CPU 之间的缓存数据，从而保证多线程或硬件驱动程序在执行时的内存顺序（Memory Ordering）

简单来说，它是多线程和底层并发编程中，防止代码被 CPU “乱序执行”而导致逻辑崩溃的隔离墙

为什么需要内存屏障：
- 单线程：为了榨干硬件性能、CPU和编译器在不改变单线程执行结果的前提下，对指令进行乱序优化

  -- 编译器重排：编译成汇编语言时，为了提高寄存器利用率，会调整指令顺序（如之前提到的 volatile 可以限制编译器重排）。

  -- CPU 乱序执行（Out-of-Order Execution）：为了绕开“内存墙”（等待内存带来的延迟），CPU 只要发现前后指令没有数据依赖，就会先执行后面的指令

  -- 多核缓存不一致：每个 CPU 核心都有自己的独立缓存（L1/L2）和写缓冲区（Store Buffer）。核心 A 修改了变量，可能还卡在自己的写缓冲区里，没有立刻刷新到主内存或其他核心可见
  
- 多线程：在单线程时乱序优化没有问题，但在多线程并发或硬件驱动开发中，这种“乱序”和“延迟”会导致毁灭性的逻辑错误（例如：明明 A 线程先写了数据，再写了标志位；B 线程却先看到了标志位，读取到的数据还是旧的）


内存屏障的作用原理：内存屏障就像一个交警，在指令流中画出一条红线，强制规定红线前后的指令不能跨越。它主要解决两个问题

- 阻止指令重排
  | 类型 | 释义 |
  | :-- | :-- |
  | LoadLoad 屏障 | 确保该屏障前的“读”操作一定先于屏障后的“读”操作完成|
  | StoreStore 屏障 | 确保该屏障前的“写”操作数据刷新到主存/缓存，先于屏障后的“写”操作|
  | LoadStore 屏障 | 确保前的“读”先于后的“写” |
  | StoreLoad 屏障 | 威力最强、开销最大。确保前的“写”必须对其他处理器可见，才允许执行后的“读”|
  
- 刷新缓存

  -- 写屏障（Write Barrier）：强制将当前 CPU 核心写缓冲区（Store Buffer）中的所有临时数据立刻刷新到 L1/L2 缓存或主存中，让其他核心可见

  -- 读屏障（Read Barrier）：强制使当前 CPU 核心的失效队列（Invalidate Queue）生效，让当前核心后续的读取操作必须去公用缓存或主存拿最新数据，而不是读自己核心的旧缓存


无锁队列（Lock-Free Queue）

- 在追求极致性能的无锁编程中（如 Linux 内核的 kfifo），多个线程通过原子操作和内存屏障来协同读写指针，完全不使用操作系统锁，从而避开线程上下文切换的开销

## 1.5、Static 和 Const

**static：静态/生命周期控制**
- 核心作用：改变变量的生命周期（存储区）或限制符号的可见性（作用域）
- 在 C 中的用法
  | 类型 | 用法 | 原理|
  | :-- | :-- |:-- |
  |静态局部变量（函数内部声明）|  在函数首次执行时初始化，函数结束后不销毁。下一次调用该函数时，它会保持上一次的值 | 将变量从栈区（Stack）移动到静态存储区（Data/BSS 段）|
  |静态全局变量 / 静态函数（在文件全局声明）|限制其文件作用域。该变量或函数只能在当前的 .c/.cpp 文件内访问，其他文件无法通过 extern 引用它|防止多个文件出现同名全局变量的命名冲突|

- 在 C++中的用法
  | 类型 | 用法 | 
  | :-- | :-- |
  |静态成员变量|属于整个类，而不是某个具体的对象。所有对象实例共享同一个静态成员。它必须在类外单独进行初始化|
  |静态成员函数|同样属于整个类，可以直接通过 类名::函数名() 调用，不需要创建对象，静态成员函数内部没有 this 指针，因此它只能访问类的静态成员，不能访问非静态成员|
  

**const：只读/常量控制**
const 的核心作用是只读限定。它告诉编译器和开发者：这个数据是“不可变”的，任何修改它的尝试都会触发编译错误
  | 类型 | 用法 | 
  | :-- | :-- |
  |基本常量| const int a = 10; 声明一个只读变量 a|
  |修饰指针| CONST TYPE   *VarName; 该指针可以修改它所指向的地址，但不能修改它所指向的值|
   | |TYPE  *CONST  VarName; 该指针可以修改它所指向的值，但不能修改它所指向的地址|
||CONST TYPE * CONST VarName;该指针即不能更改它所指向的地址，也不能修改指向地址上的值|
```shell

{
    double rates[5] = {88.99, 1001.12, 59.45, 183.11, 340.5};

    /* 该指针可以修改它所指向的地址，但不能修改它所指向的值 */
    const double *ptr1 = rates;

    double *const ptr2 = rates;

    const double * const ptr3 = rates;
    ptr3 = &rates[3]; // 不允许 assignment of read-only variable 'ptr3'
    *ptr3 = 99.88; // 不允许 Cannot assign to variable 'ptr3' with const-qualified type 'const double *const'

    getchar();
    return 0;
}
```

## 1.6、锁和原子操作
在 C 和 C++ 中，锁（Locks）和原子操作（Atomic Operations）是实现多线程同步、解决数据竞争的两大核心武器。锁属于阻塞式同步（Blocking），由操作系统内核或用户态配合管理；原子操作属于无锁同步（Lock-Free），直接映射为 CPU 的硬件指令

**锁的类型**
  | 类型 | 用法 | 
  | :-- | :-- |
  | 互斥锁（Mutex）|std::mutex：最基础的互斥锁。同一时间只允许一个线程独占。若锁已被占用，其他线程会进入睡眠状态（阻塞），等待操作系统唤醒|
  | | std::recursive_mutex（递归锁/重入锁）：允许同一个线程对同一个锁多次加锁（常用于递归函数中），而不会导致死锁。释放时需要调用相同次数的解锁|
  | | std::timed_mutex（定时锁）：支持超时机制。线程可以尝试加锁并等待一段时间（如 try_lock_for()），超时未拿到锁则放弃，避免无限死锁|
  | 自旋锁（Spinlock）| 特点：当锁被占用时，线程不进入睡眠，而是在 CPU 上执行一个死循环（忙等待）持续检查锁是否被释放|
  | | 原理：基于底层的原子操作（如 std::atomic_flag）实现|
  | | 适用场景：锁持有的时间极短。它省去了线程上下文切换（进入系统内核睡眠再唤醒）的巨大开销，但若持有时间长会极度消耗 CPU|
  |读写锁（Shared Mutex）| 标准库：C++14 引入 std::shared_timed_mutex，C++17 引入 std::shared_mutex|
  | | 特点：读共享，写独占|

**原子操作**
原子操作意味着该操作在 CPU 执行时是不可分割的单步操作。在执行期间，其他线程绝不可能看到它处于“中间状态”


## 1.7、虚函数和纯虚函数
无论是虚函数还是纯虚函数，它们在底层的实现机制都是一样的——依赖虚函数表（vtable）和虚函数表指针（vptr）
- 包含虚函数（或纯虚函数）的类，编译器会为其生成一张 vtable，里面记录了函数在内存中的实际地址
- 每一个对象实例的头部都会隐藏一个指针 vptr，指向自己类的 vtable
- 区别在于 vtable 的内容：
  
  -- 虚函数的 vtable 默认填的是基类该函数的地址；若子类重写了，子类的 vtable 就会覆盖（Override）为子类新函数的地址

  -- 纯虚函数的基类 vtable 中该位置通常填的是一个空指针（或者指向一个专门触发崩溃的系统报错函数 __purecall）。子类在继承时，必须把自己的函数地址填进去“补上这个空洞”，否则程序就无法运行
  
| 类型 | 虚函数 | 纯虚函数|
| :-- | :-- |:-- |
|维度| 虚函数 (virtual void func())|纯虚函数 (virtual void func() = 0)|
|基类是否有实现|必须有默认实现|通常没有实现（仅定义接口说明）|
|子类是否必须重写|可选|子类不重写则继承基类的默认行为|强制。子类若不实现，编译直接报错|
|所属类的状态|普通类，可以用来直接实例化创建对象|抽象类，无法实例化，只能做接口|
|引入的目的|为了实现“接口继承 + 默认实现”，允许差异化|为了实现“接口继承”，强行规范多态接口|
